headroom: fewer tokens, bigger bill

2026 jul 28

there is a category of tool that sits between your agent and the model and rewrites the conversation history to make it smaller. the pitch is simple: fewer tokens in, smaller bill. the meter on the side of the box even tells you how much you saved.

i ran one of them, headroom, across a 25-task agentic coding benchmark, three ways, and the compression was real: 39% fewer input tokens. the bill did not move. on the subset where both arms did real work, compression was more expensive than sending the full history.

the reason is prompt caching, and once you see it, the whole savings model inverts.

the control arm is the whole trick

most benchmark writeups compare a treatment against a baseline and report the delta. that tells you nothing until you know how much the harness moves on its own.

so the third arm was a control that changes the configuration without changing the work: headroom is in the path, but in a mode where it compresses zero tokens by its own accounting. baseline versus that control is the same configuration run twice. an A/A test.

it is worth saying what that arm produced, because it is the entire reason the rest of the analysis holds up. running the identical setup twice yielded a 17% apparent cost difference, with a 95% bootstrap confidence interval on the mean per-task delta that comfortably straddled zero. seventeen percent of pure noise.

if i had skipped the A/A arm, i could have run baseline against compression, computed a number in that same range, and shipped a slide saying compression saves money. the control is what turns “we measured a difference” into “we measured a difference bigger than nothing.”

the compression is real. the savings are not.

token mode cut total input tokens from 215M to 132M across the arm. that part works exactly as advertised.

the cost delta did not clear the noise floor. the treatment’s mean per-task delta landed inside the A/A band, with a Wilcoxon signed-rank p of 0.66 and a Cohen’s dz of 0.13. more tasks came out pricier with compression on than came out cheaper.

so: 39% fewer tokens, no detectable change in cost. that combination should feel wrong. tokens are what you pay for.

a cache read costs a tenth of a fresh token

it stops feeling wrong once you price the tokens correctly.

with provider prompt caching, tokens are not fungible. at published Sonnet rates, fresh input runs $3.00 per million and a cache read runs $0.30 per million. a cache read is a tenth the price. an agent loop that keeps appending to a stable prefix is close to the ideal case for this: on the baseline arm, roughly 98% of prompt tokens were cache reads.

now consider what compression does mechanically. it rewrites history. rewriting history changes the prefix. changing the prefix invalidates the cache.

the control arm busted the provider cache 14 times across 25 tasks. the compression arm busted it 123 times. cache-read reuse per write token fell from 38:1 to 11:1. compression removed tokens, and in the process pushed six million other tokens out of the cache and into full-price billing.

the arithmetic is brutal in its symmetry. the value of the lost cache discount came out within a dollar or two of the value of the compression savings. you are trading tokens at $0.30 for the privilege of sending fewer tokens at $3.00.

on a workload that already reuses the cache, shrinking the prompt costs money.

how the meter gets it wrong

headroom reports its own savings, and it reported saving real money on this run. it overstated by roughly 1.9x. the mechanism is worth describing precisely, because it is a general failure mode and not headroom’s alone.

the savings metric credits every removed token at a flat rate, around $2.00 per million. but the tokens it removes on this workload were cache reads. the cache-weighted price actually paid was about $0.79 per million. crediting a $2.00 saving for dropping a token that cost $0.79 is most of the gap.

the rest of the gap is what the metric does not do at all: it never subtracts the cache reuse the compression destroyed. it counts the tokens it removed. it does not count the tokens it knocked out of the cache somewhere else in the loop.

per task, the meter would happily report a saving on trials that came out more expensive than baseline. that is the tell. a savings number that cannot go negative is not measuring savings, it is measuring activity.

a dashboard cannot catch this

there was a monitoring dashboard for this, fed by the same emitted metrics, and it showed a healthy savings rate. it was faithfully rendering the number headroom emitted, which is exactly the problem.

the dashboard reported cost saved at roughly twice the tokens removed. the same shape i recomputed from the benchmark’s own captured emission. that ratio should be a smell: if you remove 10% of tokens and book a 19% cost cut, something is pricing the removed tokens above what they cost.

but the structural issue is deeper than a bad constant. the dashboard has no off arm. there is no counterfactual anywhere in it, and no line item for a lost cache discount. it can only ever display the gross claim. it cannot see the cache busting happening elsewhere in the loop that cancels the saving, because nothing in its data model represents “what this would have cost without me.”

instrumentation that is fed exclusively by the thing it measures will confirm that thing is working. you need an arm where the thing is off.

it did not make the agent worse

worth saying, because it is the part that survives.

solve rates were flat: 5 of 25 with compression, 4 for baseline, 4 for the control. i had subagents read the full session transcripts for every task where the arms disagreed, side by side, rather than trusting the aggregate.

the disagreements were model nondeterminism, not compression. where compression “won,” it won by spawning a research subagent, or by diagnosing the true root cause while the baseline patched the wrong layer. none of the baseline runs showed the symptoms compression is supposed to cure: no forgotten findings, no re-reading a file it had already seen. the one hard regression turned out to be an infrastructure cutoff mid-run, with the transcript ending on a credit-balance error and zero edits made.

so compression matched the baseline’s reasoning quality on 39% fewer input tokens. that is a genuinely useful result. it is just not a cost result.

the bottom line

compressing agent history works, and on a cache-heavy workload it does not save money, because the cache discount you destroy is worth about as much as the tokens you remove. before you trust a savings meter, check whether it prices removed tokens at what you actually paid for them, and whether it can report a negative number at all.

and run the A/A arm. the gap between “different” and “different from noise” was 17 percentage points here, which is more than large enough to have shipped the wrong conclusion.

where compression still earns its place is when you are up against a context window rather than a budget. matching baseline reasoning on 39% fewer tokens is real. it is just a memory result wearing a cost result’s clothes.
